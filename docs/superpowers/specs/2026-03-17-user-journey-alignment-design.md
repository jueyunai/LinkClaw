# LinkClaw 用户旅程对齐与主链路补齐设计

> 日期：2026-03-17
> 范围：文档对齐 + 主链路缺口修补

## 目标

将用户旅程文档与当前实现对齐，并补齐最影响核心体验的四个缺口：

1. 注册后显式创建 `profiles`
2. 首次登录后的资料完善轻引导
3. 活动详情页展示真实报名状态
4. 嘉宾邀请列表展示 `ai_match_reason`

本轮不扩展到取消报名、统计看板或更大范围权限重构，避免偏离主链路修补目标。

## 设计原则

- 优先让文档准确反映“当前实现 + 本轮目标”，避免把规划能力写成已实现能力。
- 以最小改动补齐主链路，不做无关重构。
- 权限继续保持“middleware 负责登录门槛，页面与 Server Action 负责角色/资源校验”的模式。
- AI 能力在文档层表述为“推荐系统 + 缓存 + fallback”，不绑定单一 provider 名称。

## 实现设计

### 1. 注册后显式创建 `profiles`

位置：`src/app/[locale]/auth/actions.ts`、`src/app/[locale]/auth/callback/route.ts`

设计：
- 覆盖两条首次建档链路：邮箱注册成功后、OAuth 首次登录回调成功后。
- 最小字段：`id`、`role`、`display_name`；如能从 auth metadata 取到 `bio`、`industry`、`city` 以外的值，则仍以最小建档为主，不额外扩展。
- 为避免重复写入，先检查是否已有同 ID 记录，再决定是否插入。
- 若记录缺失但 auth 用户已存在，应允许在后续登录时补建，避免出现永久半成功状态。
- 若写入失败，应返回用户可理解的错误或进入可恢复分支，而不是静默忽略。

### 2. 首次资料完善轻引导

位置：`src/app/[locale]/page.tsx`

设计：
- 当用户已登录且 profile 关键字段不足时，在首页推荐区前或主内容顶部显示提示卡。
- 引导文案提供前往 `/profile` 的入口。
- 关键字段先采用轻量标准：`bio`、`industry`、`city` 任一缺失即提示。
- 若 `profiles` 记录不存在，也应进入同一提示分支，而不是静默当作完整资料用户处理。
- 不做强制跳转，不阻断浏览活动。

### 3. 活动详情页展示真实报名/邀请状态

位置：`src/app/[locale]/events/[id]/page.tsx`

设计：
- 详情页查询需至少包含 `registrations.type` 与 `registrations.status`，不能只查 `status`。
- 对 `type=applied`：展示“待审核 / 已通过 / 已拒绝”等报名状态。
- 对 `type=invited`：展示“已获邀请 / 已接受邀请 / 已拒绝邀请”等邀请语义，避免误显示为“已报名”。
- 本轮详情页不承担邀请处理入口；邀请接受/拒绝仍在 `/my-events` 完成，详情页只做状态展示与说明。
- 若存在记录，报名按钮应改为禁用或替换为对应状态提示，防止误导成统一“已报名”。

### 4. 邀请列表展示 `ai_match_reason`

位置：`src/app/[locale]/my-events/page.tsx`

设计：
- guest 邀请列表查询补充 `ai_match_reason` 字段。
- 在邀请卡片中展示推荐理由，作为接受/拒绝前的辅助信息。
- 若理由为空，则不展示该区块。
- 当前允许 `ai_match_reason` 以单语文本展示；若未来需要严格双语，再单独扩展字段或翻译策略。

### 5. 文案同步

位置：`messages/zh.json`、`messages/en.json`

设计：
- 本轮新增或调整的状态文案、首页轻引导文案、邀请理由标题，需同步更新中英文消息文件。
- 避免直接在页面硬编码中文或英文字符串。

## 数据流与边界

- `profiles` 仍作为用户画像主来源。
- `registrations` 继续承担 applied / invited 两种记录形态。
- `ai_match_reason` 属于邀请上下文附加信息，只在相关邀请视图消费。
- 首页轻引导仅依赖当前 profile 完整度判断，不引入额外表或状态机。

## 错误处理

- 注册后 profile 创建失败：在 auth 流程内明确返回失败信息，避免出现“Auth 成功但业务 profile 缺失”的半成功状态。
- 首页 profile 不完整：仅展示提示，不视为错误。
- 邀请缺少 `ai_match_reason`：安静降级为不显示理由。

## 验证策略

1. 手工验证
   - 注册 guest / organizer 后确认 `profiles` 记录存在
   - 首次登录且画像不完整时首页出现引导
   - 活动详情页显示真实报名状态
   - guest 在 `/my-events` 可看到邀请理由
2. 自动化验证
   - 视实现情况补充最小粒度的组件或页面测试
   - 至少运行与改动相关的现有测试与 lint

## 非目标

本轮不包含：
- 取消报名
- 管理页统计看板
- 全量权限前移到 middleware
- 大范围推荐系统重构

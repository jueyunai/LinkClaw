# LinkClaw 第一版全站交互规范基线设计

> 日期：2026-03-18
> 范围：定义第一版全站统一交互规则，并在本轮先落地到活动创建页与活动管理页，作为后续全站迁移样板

## 目标

为 LinkClaw 建立一套可复用、可扩展的第一版全站统一交互规则，优先解决当前活动管理域中最明显的两类问题：

1. 主操作按钮布局不符合常见用户习惯，存在左侧漂浮、视觉重心不稳定的问题。
2. 点击提交型按钮后界面缺少即时反馈，用户在 Server Action 执行期间感知为“没有响应，过几秒突然完成”。

本轮同时达成两个层面的目标：

- **规范层**：沉淀全站统一的主操作布局、提交态反馈、结果态提示规则。
- **实现层**：先在 `events/new` 与 `events/[id]/manage` 两类典型页面完成落地，为后续全站迁移提供交互原语与样板。

> 注意：本轮是“全站统一交互规则的第一版基线”，不是“所有现有提交入口都已完成迁移”。

## 设计原则

- **即时反馈优先**：所有提交型操作在点击后必须立刻给出可见反馈，不能静默等待。
- **主操作右对齐**：遵循常见表单与后台管理界面习惯，主操作统一靠右布局。
- **规则先于页面**：优先抽出可复用交互原语，而不是在每个页面重复写局部样式与逻辑。
- **兼容现有 Server Action 模式**：本轮不推翻当前 redirect 驱动的提交流程，而是在现有架构上补齐提交态与结果态体验。
- **最小复杂度落地**：不引入乐观更新、全局 toast 主导策略或大范围 action 重构。
- **边界清晰**：本轮只统一交互展示，不改 middleware、权限模型或 Server Action 鉴权策略。

## 现状映射

本轮实现与以下现有文件直接相关：

- 页面
  - `src/app/[locale]/events/new/page.tsx`
  - `src/app/[locale]/events/[id]/manage/page.tsx`
- Server Actions
  - `src/app/[locale]/events/actions.ts`
  - `src/app/[locale]/registrations/actions.ts`
- 非功能边界参考
  - `src/middleware.ts`
- 国际化文件
  - `messages/zh.json`
  - `messages/en.json`

### 当前管理页的提交入口分布

`src/app/[locale]/events/[id]/manage/page.tsx` 不是单一大表单，而是多个独立提交入口并存：

1. **页面头部状态操作**
   - 发布
   - 下架 / 重新发布
   - 每个按钮各自位于独立 `<form action={updateEventStatus}>`

2. **活动信息编辑区**
   - 保存修改
   - 一个独立 `<form action={updateEvent}>`

3. **推荐嘉宾卡片区**
   - 发送邀请
   - 每张卡片各自独立 `<form action={inviteGuest}>`

4. **报名申请卡片区**
   - 通过
   - 拒绝
   - 每条申请至少包含两个独立提交动作

这意味着本轮规范必须适配“**多个独立 form 并存于同一页面**”的现实，而不是只面向单表单页设计。

## 问题分析与根因

### 1. 按钮布局问题

当前活动管理页中的保存按钮容器位于左侧：
- `src/app/[locale]/events/[id]/manage/page.tsx`

这会导致：
- 表单填写完后的视觉收束点不在右下角，和常见后台表单习惯不一致。
- 在同页其它操作（发布、下架、邀请、审核）已经偏向右侧或分散布局的情况下，整体交互语言不统一。

### 2. “点击后几秒没反馈”的体感问题

当前保存、发布、邀请、审核等操作都走 Server Action：
- `src/app/[locale]/events/actions.ts`
- `src/app/[locale]/registrations/actions.ts`

以保存活动为例，点击后会经历：
1. 提交表单
2. Server Action 进行用户校验 / 角色校验
3. 解析表单并校验
4. Supabase 读写
5. redirect 返回目标页
6. 页面重新渲染并展示 success / error

问题不在于已证明存在单一慢查询，而在于：
- 前端当前**没有 pending 态 UI**
- 用户无法确认点击是否生效
- 只能在 redirect 完成后突然看到结果

因此本轮的首要修复方向是：**补齐交互层的提交中反馈**，而不是先假设数据库或网络是主要瓶颈。

## 全站统一交互规则

### 1. 操作分类

本项目的用户触发操作统一分为以下两类：

1. **提交型操作**
   - 例如：保存修改、保存草稿、立即发布、发布、下架、邀请、通过申请、拒绝申请、退出登录、报名参加
   - 特征：会发起 Server Action 或其他异步提交
   - 规则：必须具备 pending 态、禁用重复提交、结果提示策略

2. **导航型操作**
   - 例如：查看活动、进入详情页、跳转到资料页
   - 特征：不产生业务写入
   - 规则：遵循普通按钮/链接规则，不强制使用 pending 文案

本轮重点落地提交型操作中的“活动管理域”，其他入口如退出登录、报名参加等暂不迁移，但后续需复用本轮原语。

### 2. 布局规则

#### 表单底部操作区

- 表单底部操作区统一右对齐。
- 单个主操作按钮：直接放右侧。
- 多个操作按钮：整体右对齐，主操作放最右，次操作在左。
- 在窄屏下允许自动换行，但容器默认仍保持 `justify-end`。
- `FormActions` 默认使用：
  - 横向排列
  - `gap` 统一
  - `flex-wrap`
  - `justify-end`

#### 卡片/列表中的操作区

- 卡片内部的提交型操作，统一放在当前卡片内容区的末尾。
- 若存在多个按钮，使用统一操作区容器，保持“次操作在左，主操作在右”的顺序。
- 避免将单个主提交按钮放在卡片左下角孤立出现。

### 3. 提交态规则

所有提交型操作必须满足：

- 点击后立即进入 pending 态。
- pending 时按钮禁用，避免重复提交。
- pending 时按钮文案切换为对应动作的进行中形式。
- pending 与 idle 切换时尽量保持按钮宽度稳定，避免视觉跳动。

可执行约束：
- 通过固定内边距、最小宽度或稳定文案长度策略，避免按钮在 pending 时明显变窄或变宽。
- `PendingSubmitButton` 只负责当前按钮自身展示，不负责全局 loading 蒙层。

统一文案映射：

- 保存类：`保存中...`
- 发布类：`发布中...`
- 下架/关闭类：`处理中...`
- 邀请类：`邀请中...`
- 审核类：`处理中...`

英文文案对应：

- `Saving...`
- `Publishing...`
- `Processing...`
- `Inviting...`

### 4. 结果反馈规则

- 全站提交型操作的主要结果反馈统一以**页面内结果提示区**为主。
- 成功与失败都优先使用页面内提示区，而不是以 toast 作为主通道。
- 结果提示区应位于当前页面主内容的上方或当前模块的上方，确保用户提交后可在结果返回时直接感知。
- 现有 redirect + query 参数 `success` / `error` 模式本轮继续保留。

### 5. 当前 success / error 形态约束

当前代码中：
- `success` 大多是稳定枚举值，例如 `updated`、`published`、`application_accepted`
- `error` 则常常是直接透传中文文案或 Supabase `error.message`

因此本轮只做以下统一：
- **统一 pending 反馈**
- **统一页面内结果提示区样式与位置策略**
- **统一 success 展示逻辑所需的按钮与文案协作**

本轮**不**解决以下问题：
- 将所有 `error` 统一为错误码
- 将所有 `error` 完整国际化
- 重写 action 返回协议

这部分明确列为后续交互与错误语义治理的第二阶段工作。

### 6. 一致性规则

- 相同类型的动作应使用相同语义层级的按钮样式。
- 相同类型的 pending 文案应全站统一。
- 同一种成功/失败结果展示方式应全站统一，避免某些页面顶部提示、某些页面静默、某些页面只改按钮文案。

## 国际化规则

### 1. pending 文案归属

pending 文案不应散落到 `events`、`myEvents` 等业务 namespace 中。

本轮建议新增统一公共命名空间，例如：
- `common.pending.saving`
- `common.pending.publishing`
- `common.pending.processing`
- `common.pending.inviting`

这样后续退出登录、报名参加、资料保存等动作也可以直接复用。

### 2. 已知边界

当前 redirect 返回的 `error` 文案中，仍存在：
- 直接中文字符串
- 直接透传第三方错误信息

因此本轮国际化目标仅包括：
- pending 按钮文案双语化
- 页面中新增或调整的稳定 success 文案继续走翻译 key

本轮不承诺完成全量 `error` 国际化。

## 推荐实现方式

### 1. 提交按钮原语

新增一个轻量客户端组件，例如：
- `src/components/ui/pending-submit-button.tsx`

职责：
- 基于 `useFormStatus()` 读取**当前 form** 的提交状态
- 统一管理 idle / pending 文案切换
- 自动禁用按钮
- 透传现有 `Button` 样式能力（variant、size、className）

边界：
- `PendingSubmitButton` 的 pending 作用域仅限**所在 form**。
- 它不负责跨 form 联动，不负责同页多个独立提交按钮之间的互斥。
- 若某组按钮需要共享一个 pending 态，则它们必须放在同一个 form 中。

### 2. 操作区布局原语

新增一个轻量布局组件，例如：
- `src/components/ui/form-actions.tsx`

职责：
- 提供统一的右对齐操作区容器
- 统一 gap、换行、主操作落点规则
- 同时适用于表单底部和卡片操作区

边界：
- 该组件只负责布局约束，不处理业务状态。

### 3. 页面结果提示保持现有模式

当前管理页已存在 success / error 提示区。
本轮不新增全局结果框架，而是：
- 继续使用当前 `success` / `error` query 参数模式
- 尽量将页面内结果提示集中在主内容顶部
- 让页面内结果提示区成为固定规范

其中 `events/new` 是本轮的明确特例：
- 创建失败仍留在当前页展示 `error`
- 创建成功继续沿用现有 redirect 逻辑，跳转到 `events/[id]/manage?success=...`
- 成功结果提示显示在跳转后的管理页，而不是强行回到创建页原位展示

这样可以在不重构 action 返回机制的前提下，快速落地统一体验。

## 暂不纳入本轮的事项

本轮不包含：

- 将所有 Server Action 改造为无 redirect 的局部更新模式
- 引入 toast 作为主反馈机制
- 统一改造全站所有历史页面
- 乐观更新
- 独立的全局交互状态管理层
- 全量错误码化与错误国际化
- middleware 受保护路由集合调整
- Server Action 权限策略重构

## 数据流与交互流

### 保存 / 发布 / 邀请 / 审核的统一交互流

1. 用户点击按钮
2. 按钮立即进入 pending 态
3. 按钮禁用，防止重复提交
4. Server Action 执行
5. 页面 redirect / 刷新返回
6. 页面顶部或模块顶部显示 success / error 结果提示
7. 按钮恢复 idle 状态

### 用户感知目标

用户在任何提交动作上都应获得以下感知：
- 我刚刚的点击已被系统接收
- 系统正在处理
- 结果已经明确返回

## 验证策略

### 手工验证

#### 中文 / 英文 locale 都要验证

必须分别在 `zh` 与 `en` 下验证以下场景：

1. 活动创建页
   - 点击保存草稿后按钮立即变化
   - 点击立即发布后按钮立即变化
   - 操作区右对齐
   - pending 文案与 locale 一致

2. 活动管理页
   - 保存修改按钮位于右侧
   - 发布 / 下架按钮提交时立即进入 pending
   - 邀请按钮提交时立即进入 pending
   - 通过 / 拒绝报名按钮提交时立即进入 pending
   - 成功 / 失败结果仍能稳定显示
   - success 文案与当前 locale 一致

3. 重复提交保护
   - 在 pending 期间无法重复点击同一按钮

### 自动化验证

自动化验证以当前仓库测试结构为准：
- 以交互原语组件单测为主
- 页面级测试只验证渲染结构、按钮文案和交互态存在
- 不依赖真实 Supabase 或 middleware
- 需要翻译时沿用现有 `next-intl` mock 模式
- 参考现有测试风格：`test/app/profile-page.test.tsx`

至少运行：
- 与本轮改动相关的测试
- lint

## 非目标

本轮不解决以下问题：
- 后端真实性能瓶颈分析与压测
- 全站所有历史页面一次性改造
- 全局 toast / 通知中心设计
- 全量错误码设计
- 全量错误国际化
- middleware 与权限模型重构

## 成功标准

本轮完成后，应满足：

1. 活动创建页与活动管理页的主操作按钮布局统一为右对齐。
2. 所有提交型按钮点击后都能立即展示 pending 状态。
3. 所有提交型按钮在 pending 期间禁止重复提交。
4. 页面结果提示继续稳定可见，且与 pending 反馈形成完整闭环。
5. 中文与英文 locale 下的 pending 文案与成功提示均能正确工作。
6. 新增交互原语可供后续全站页面复用，而不需要重复实现局部逻辑。

# 基于 OpenClaw 的智能体借鉴与 LinkClaw 双智能体推荐策划

## 1. 目标与范围

**目标**：借鉴 OpenClaw 的“多智能体 + 插件/技能 + 记忆”能力，将 LinkClaw 当前的“AI 推荐”升级为“嘉宾智能体 + 主办方智能体”双智能体体系：

- **嘉宾智能体（Guest Scout）**：在活动广场中自动搜索、筛选并生成适合该嘉宾的活动推荐与理由。
- **主办方智能体（Organizer Scout）**：在嘉宾池中自动筛选并匹配适合某活动的嘉宾名单，输出推荐邀请清单与理由。

**范围**：本方案聚焦业务与技术策划，输出可落地的阶段性实现路线与架构建议；不直接改代码。

---

## 2. OpenClaw 调研摘要（可借鉴能力）

### 2.1 核心定位与架构

- **定位**：个人 AI 助手，核心为“Gateway 控制平面”，负责会话、工具、渠道与事件的统一调度（README）。
- **多智能体**：支持按 workspace + session 进行 agent 隔离与路由（README）。
- **工具体系**：工具（tools）与插件（plugins）解耦，功能可按需启用（docs/tools/plugin.md）。
- **技能体系**：技能目录（SKILL.md）可按 agent/workspace/全局分层加载，支持优先级与 gating（docs/tools/skills.md）。

### 2.2 插件与技能的关键设计

- **插件（Plugin）**：通过 manifest + JSON Schema 声明配置与能力，运行时加载；可注册工具、HTTP 路由、CLI 命令、服务等（docs/tools/plugin.md）。
- **技能（Skills）**：按“bundled / managed / workspace”三层来源加载，agent 级别隔离，支持 gating（依赖环境、配置、平台）与安全隔离（docs/tools/skills.md）。

### 2.3 记忆与检索

- **Memory 插件**：内置“memory-core / memory-lancedb”插件槽位（docs/tools/plugin.md）。
- **LanceDB 长期记忆**：向量检索 + 自动记忆捕获/召回；内置触发规则与类别标签（extensions/memory-lancedb/index.ts、config.ts）。
- **Embedding 管理**：支持自定义模型与向量维度；可配置自动捕获、自动召回与最大文本长度（extensions/memory-lancedb/config.ts）。

### 2.4 JSON 任务与工作流

- **llm-task 插件**：提供“JSON-only”结构化任务调用能力（extensions/llm-task/README.md）。
- **Lobster 插件**：工作流外壳 + 工具调用桥接，适合审批、自动化流程（extensions/lobster/README.md）。

### 2.5 安全与运营

- **安全默认策略**：渠道对未知来源默认“配对/白名单”策略；非 main 会话可沙箱化（README）。
- **观测性**：OpenTelemetry 诊断插件（extensions/diagnostics-otel）。

**可借鉴结论**：
1. **多智能体按“职责 + workspace + 会话”隔离**。
2. **插件/技能作为可选能力层**，减少核心耦合。
3. **记忆与向量检索**让推荐具备“长期偏好/历史行为”能力。
4. **JSON-only 任务工具**适合推荐评分、标签提取、摘要归纳等可验证任务。

## 3. LinkClaw 现状与差距

### 3.1 现状

- 首页推荐只在 **guest** 场景下启用，逻辑在 [src/lib/ai/mock-recommendation.ts](../src/lib/ai/mock-recommendation.ts)。
- 推荐产出结构简单（理由 + 事件列表），无长期记忆、无组织方智能体、无可解释的匹配流程。

### 3.2 差距

- **缺少角色化智能体**（guest/organizer 分治）。
- **缺少记忆/偏好向量化**能力。
- **缺少可控的任务与安全策略**（工具白名单、审批等）。
- **缺少可观察性与反馈闭环**（推荐是否被接受、拒绝原因）。

## 4. 双智能体推荐总体方案

### 4.1 角色定义

| 角色 | 智能体名称 | 目标 | 输入 | 输出 |
|---|---|---|---|---|
| 嘉宾 | Guest Scout | 找到适合嘉宾的活动 | 嘉宾资料、历史报名、偏好、活动库 | 活动推荐列表 + 理由 |
| 主办方 | Organizer Scout | 找到适合活动的嘉宾 | 活动信息、目标画像、嘉宾池 | 推荐嘉宾列表 + 理由 |

### 4.2 触发方式

- **主动触发**：
  - 嘉宾登录首页/刷新推荐。
  - 主办方进入活动详情页/“邀请嘉宾”页面。
- **定时触发（批量）**：
  - 每日/每小时批量刷新热门活动与重点嘉宾的推荐结果。

### 4.3 推荐输出形态

- **嘉宾侧**：
  - 推荐活动卡片 + “为什么适合你”理由。
  - 过滤后仍保留“探索活动”入口。
- **主办方侧**：
  - 推荐嘉宾列表 + “匹配点”理由。
  - 一键邀请（可走审批或二次确认）。

## 5. 数据与记忆设计（借鉴 OpenClaw）

### 5.1 记忆模型（Memory）

借鉴 OpenClaw memory-lancedb：

- **长期记忆表（ai_memories）**
  - `id`, `user_id`, `role`(guest/organizer), `text`, `category`(preference/fact/decision/entity/other), `embedding`, `created_at`。
- **触发策略**
  - 用户显式偏好、报名/邀请反馈、长期行为模式 -> 自动 capture。
- **召回策略**
  - 推荐时从记忆库召回 top-k 相似偏好/历史结果。

### 5.2 数据表与任务记录（可选）

- `ai_agent_tasks`：任务请求、输入摘要、状态。
- `ai_agent_runs`：实际执行记录（版本、模型、耗时）。
- `ai_recommendations`：输出结果、理由、评分。
- `ai_feedback`：用户对推荐的操作（点击、报名、忽略、拒绝）。

## 6. 推荐算法设计

### 6.1 候选集生成（硬过滤）

- 角色匹配（guest 仅看公开活动，organizer 仅看候选嘉宾）。
- 活动状态（published / closed）。
- 时间冲突与地点限制。
- 主办方条件（技能、性别/年龄/地区等若存在）。

### 6.2 评分与排序（软匹配）

- **Embedding 相似度**：活动描述 vs 嘉宾偏好记忆。
- **规则分**：如兴趣标签重叠、历史报名相似度、组织方偏好。
- **多样性约束**：避免推荐过度集中在单一类型活动。

### 6.3 解释生成

- 每条推荐生成 1-2 条理由（例如：
  - “你过去报名过相似的户外活动”
  - “活动时间与空闲时段匹配”）。

## 7. LLM 接入与“嘉宾-活动”分身智能体互聊匹配

### 7.1 LLM 介入点

- 画像理解与偏好抽取：从 profile/历史行为生成结构化画像与标签。
- 语义召回：活动/嘉宾文本向量化，召回 top-k。
- 结构化评分：JSON-only 任务输出评分/匹配点/风险。
- 解释生成：面向用户的推荐理由。
- 冷启动问答：轻量问卷/对话补足偏好。

### 7.2 “嘉宾智能体 ↔ 活动智能体”互聊机制

- 每个活动生成一个“活动分身智能体（Activity Agent）”，上下文包含活动信息、主办方偏好、限制条件。
- 嘉宾智能体上下文包含个人资料、记忆召回与历史反馈。
- 匹配时由两者进行**受控的短对话**，目标是输出结构化匹配结论，而非直接对用户发送消息。
- 对话输出统一为：
  - `match_score`
  - `fit_reasons`
  - `risks_or_gaps`
  - `questions_for_user`（需要用户补充的信息）
- 对话摘要写入推荐记录，供前端展示与后续反馈学习。

### 7.3 运行控制与安全

- 对话仅用于推荐，不触发副作用；邀请发送仍需主办方确认。
- 设定**最大轮数/Token/成本**与超时策略。
- 工具白名单：仅允许检索、评分、解释，不允许写入/外部通知。
- 全量审计：记录输入摘要、输出与模型版本，便于回溯。

## 8. 智能体能力分层（借鉴 OpenClaw 插件/技能）

### 8.1 工具层（Tool）

- `search_events`：筛选活动候选集。
- `search_guests`：筛选嘉宾候选集。
- `score_match`：评分计算（可 JSON-only）。
- `explain_match`：生成推荐理由。
- `send_invite`：发送邀请（需审批/白名单）。

### 8.2 技能层（Skill）

- **Guest Scout Skill**：组合调用 `search_events` + `score_match` + `explain_match`。
- **Organizer Scout Skill**：组合调用 `search_guests` + `score_match` + `explain_match`。

### 8.3 记忆层（Memory）

- 自动 capture：从报名/邀请/反馈中提取偏好。
- 自动 recall：在推荐时注入偏好记忆。

## 9. 系统架构建议（LinkClaw 落地）

### 8.1 推荐服务位置

建议在 [src/lib/ai/](../src/lib/ai/) 下新增：

- `agent/guest-scout.ts`
- `agent/organizer-scout.ts`
- `memory/`（Embedding + Recall + Capture）

### 8.2 执行方式选择

- **短期（MVP）**：
  - 使用 Server Actions 或 API Route 按需调用推荐逻辑。
- **中期**：
  - 接入定时任务（Supabase cron / Vercel cron）批量生成推荐结果。
- **长期**：
  - 形成独立“AI 推荐服务”或 Edge Function。

### 8.3 安全与审批

- 推荐本身无副作用，可直接展示。
- **邀请发送**属于“副作用操作”，需：
  - 审批（主办方确认）
  - 白名单（只允许组织者执行）
  - 限流（防止滥用）

## 10. MVP 阶段路线图

### Phase 0：数据准备
- 补齐活动与嘉宾标签/偏好字段。
- 统一活动与嘉宾画像结构。

### Phase 1：嘉宾智能体上线
- 仅在首页推荐中替换 mock 逻辑。
- 输出推荐理由 + 活动排序。

### Phase 2：主办方智能体上线
- 在活动详情页提供“推荐嘉宾”模块。
- 输出推荐嘉宾 + 理由 + 邀请入口。

### Phase 3：记忆与反馈闭环
- 记录用户反馈与报名结果。
- 形成长期偏好记忆并用于召回。

---

## 11. 风险与开放问题

1. **数据稀疏**：新用户缺少历史偏好，需冷启动策略（热门活动 + 轻量问卷）。
2. **算法解释**：理由质量决定推荐可信度，需要稳定模板与可信特征。
3. **隐私与安全**：嘉宾画像与推荐过程需符合隐私合规要求。
4. **成本控制**：Embedding 与 LLM 推理成本需限额与缓存策略。

---

## 12. 结论

OpenClaw 的可借鉴点集中在：

- **多智能体隔离与路由**
- **插件/技能解耦能力**
- **记忆与向量检索**
- **JSON 结构化任务工具**

LinkClaw 可在现有推荐逻辑上逐步引入：

- 角色化智能体（嘉宾/主办方）
- 记忆与召回（长期偏好）
- 结构化评分与解释

最终形成一个可控、可解释、可迭代的双智能体推荐体系。
